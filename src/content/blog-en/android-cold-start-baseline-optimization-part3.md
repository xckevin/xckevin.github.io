## Test results

SM-A5070, Android 11, API 30

Measurement range: from `Application.attachBaseContext` to `HomeActivity.onResume`

### Conclusion

1. The better the phone's performance, the less visible the optimization effect becomes.
2. The improvement did not reach the 20%+ figure described in Google's official documentation. In our tests, the better cases were around 10%.
3. The baseline file tells the system which code should be compiled to binary ahead of time. The multinational and India environments share similar logic in most cases, so packaging both environments with the same file has little impact.

### Post-launch expectations

Overall, the optimization should help, but the effect is unlikely to be dramatic. We expect the gain to stay below 10% for three reasons.

Reference: <https://developer.android.com/topic/performance/baselineprofiles/create-baselineprofile?hl=en#baseline-profile-library>

### 2. How can different baseline files be generated and applied for multiple product flavors?

After configuration, two Gradle tasks are generated:

![](../../assets/android-%E5%86%B7%E5%90%AF%E5%8A%A8%E4%BC%98%E5%8C%96--baseline-%E4%BC%98%E5%8C%96-23.png)

After the task completes, it generates two different `baselineProfile` files for two different flavor packages. They need to be added manually, and the integration with the existing packaging mechanism still needs to be considered.

**Phase 1: manually produce productFlavor artifacts for the India and multinational environments**

Place the India and multinational artifacts under the `India` and `Others` directories respectively:

![](../../assets/android-%E5%86%B7%E5%90%AF%E5%8A%A8%E4%BC%98%E5%8C%96--baseline-%E4%BC%98%E5%8C%96-24.png)

When running the packaging command, use a custom script to copy either the `india` or `others` file into the main project. This allows each flavor to package with its corresponding baseline file and integrates with the existing Starlink packaging flow:

```plain
if (isPackOtherApk()) {
    task copyTxtFile(type: Copy) {
        from '../app/src/others/baseline-prof.txt'
        into '../app/src/main/'
    }
    preBuild.dependsOn(copyTxtFile)
} else if (isPackIndiaApk()) {
    task copyTxtFile(type: Copy) {
        from '../app/src/india/baseline-prof.txt'
        into '../app/src/main/'
    }
    preBuild.dependsOn(copyTxtFile)
}
```

We considered placing the file under `assets`, but files in that directory are not removed after packaging, which increases APK size. The directory is also usually added to `.gitignore`, so Git cannot track it. We also considered the `raw` directory, but it has naming-rule restrictions, and the original artifact is still not removed after packaging, which creates the same APK-size issue.

**Phase 2**: full process automation, not yet implemented.

### 3. What is the difference between systemImageSource = "aosp" and systemImageSource = "google"?

- **Google API**: a set of application programming interfaces provided by Google for developers to integrate with Google services and platforms, including Google Maps, Drive, Calendar, Analytics, Cloud Vision, and more.
- **AOSP**: Android Open Source Project, the open source Android codebase. Another reason to use AOSP is that it is easier to root.

Reference: <https://developer.android.com/reference/tools/gradle-api/7.4/com/android/build/api/dsl/ManagedVirtualDevice#systemImageSource()>

### 4. How can the before-and-after optimization effect be validated without automated tests?

#### Manually measuring app improvement

First, measure the unoptimized app startup time as a baseline:

```plain
PACKAGE_NAME=com.example.app

# Force Stop App
adb shell am force-stop $PACKAGE_NAME
# Reset compiled state
adb shell cmd package compile --reset $PACKAGE_NAME

# Measure App startup
# This corresponds to `Time to initial display` metric
# For additional info https://developer.android.com/topic/performance/vitals/launch-time#time-initial
adb shell am start-activity -W -n $PACKAGE_NAME/.ExampleActivity \
 | grep "TotalTime"
```

Next, sideload the Baseline Profile.

**Note**: This workflow applies only to Android 9, API 28, through Android 11, API 30.

```plain
# Unzip the Release APK first
unzip release.apk

# Create a ZIP archive
# Note: The name should match the name of the APK
# Note: Copy baseline.prof{m} and rename it to primary.prof{m}
cp assets/dexopt/baseline.prof primary.prof
cp assets/dexopt/baseline.profm primary.profm

# Create an archive
zip -r release.dm primary.prof primary.profm

# Confirm that release.dm only contains the two profile files:
unzip -l release.dm
# Archive:  release.dm
#   Length      Date    Time    Name
# ---------  ---------- -----   ----
#      3885  1980-12-31 17:01   primary.prof
#      1024  1980-12-31 17:01   primary.profm
# ---------                     -------
#                               2 files

# Install APK + Profile together
adb install-multiple release.apk release.dm
```

Verify whether the package was optimized at install time:

```plain
# Check dexopt state
adb shell dumpsys package dexopt | grep -A 1 $PACKAGE_NAME
```

The output should show that the package has been compiled:

```plain
[com.example.app]
  path: /data/app/~~YvNxUxuP2e5xA6EGtM5i9A==/com.example.app-zQ0tkJN8tDrEZXTlrDUSBg==/base.apk
  arm64: [status=speed-profile] [reason=install-dm]
```

Now measure app startup performance in the same way as before, but **do not reset the package's compilation state**:

```plain
# Force Stop App
adb shell am force-stop $PACKAGE_NAME

# Measure App startup
adb shell am start-activity -W -n $PACKAGE_NAME/.ExampleActivity \
 | grep "TotalTime"
```

### 6. Obfuscation-related issues

First, do not enable `minifyEnabled` when generating `baseline-prof.txt`, or configure rules separately so the relevant code is not obfuscated. Otherwise, the recorded hot code will be the obfuscated code.

So if Baseline Profiles record the paths of hot classes, and obfuscation changes class paths, can Baseline Profiles still work when building the final release package?

Most official documentation does not mention this point. In a related issue, a Google developer replied:

> _Baseline profiles also participate in the obfuscation process, like classes; so this already works._

Reference: <https://issuetracker.google.com/issues/235571073#comment2>

Google confirmed that Baseline Profiles can already work correctly with R8 optimization. Test validation also showed that after enabling `minifyEnabled`, Macrobenchmark still produced better startup-speed results.

### 7. Code from Dynamic Feature Modules is missing from the benchmark APK

Multiple tabs on our app's home page are implemented through Dynamic Feature Modules, so the package produced by the benchmark test does not include the related code. The home page appears blank.

Related discussion: <https://stackoverflow.com/questions/71706002/android-jetpack-baseline-profile-with-dynamic-feature-modules>

> Same issue here, it looks like when we run benchmark task, the task didn't include the dynamic feature code into our application, basically it will use app bundle(aab) instead of apk. So if the class is not included in your base.apk, then it will throw a classnotfound exception

**Cause**: the Gradle command for the baseline test is `:benchmark:connectedIndiaBenchmarkAndroidTest`. The final packaging command in its task chain is `:app:packageIndiaBenchmark`, and that APK does not include Dynamic Feature Module artifacts. Only `:app:packageIndiaBenchmarkUniversalApk` includes Dynamic Feature Module code in the package.

**Temporary workaround**: after `:app:packageIndiaBenchmark` completes, replace the benchmark artifact with the package produced by `:app:packageIndiaBenchmarkUniversalApk`. The accuracy and code quality of this workaround still need improvement. Google is expected to provide an official solution later.

### 8. Automated testing issue

Our app displays a notification-permission dialog. Once it appears, it sits at the top of the view hierarchy and breaks ID-based automated test logic. Use `allowNotifications()` to dismiss the dialog:

```plain
fun MacrobenchmarkScope.allowNotifications() {
    if (SDK_INT >= TIRAMISU) {
        val command = "pm grant $packageName ${permission.POST_NOTIFICATIONS}"
        device.executeShellCommand(command)
    }
}

private fun startup(compilationMode: CompilationMode) {
    benchmarkRule.measureRepeated(packageName = PACKAGE_NAME,
        // metrics = listOf(TraceSectionMetric("app-start")),
        metrics = listOf(StartupTimingLegacyMetric()),
        iterations = 5,
        startupMode = StartupMode.COLD,
        compilationMode = compilationMode,
        setupBlock = {
            pressHome()
            allowNotifications()
        }) {
        startActivityAndWait()
        allowNotifications()
        device.wait(Until.hasObject(By.res("com.urbanic:id/include_navigation_bottom")), 5_000)
    }
}
```

## Remaining questions

1. **Why is precompilation with the baseline file sometimes slower than no precompilation?**  
   The reason is the same as point 2 above.

2. **Why does full AOT not show an obvious improvement?**  
   The device test environment can differ at different times, so the effect may not always improve. We recommend testing in groups of 5 iterations; if time allows, use groups of 10. Use the latest versions of AGP, such as 7.3.0-rc01, Macrobenchmark 1.2.0-alpha03, and ProfileInstaller 1.2.0. Device load may vary over time, so increasing the iteration count can produce more consistent results. Reference: <https://stackoverflow.com/questions/73639422/baseline-profiles-metrics-are-not-consistent>

3. **How should startup effects be counted across multiple dimensions?**  
   For example, compare the effect for newly installed versions versus existing versions after this optimization is applied. Users on the latest version are mostly newly installed users, so they can serve as the baseline for newly installed version data.

4. **How can other factors that affect a specific app version's startup speed be isolated?**  
   This still needs further exploration.
